# 分离目标监控范围与实际监听覆盖

全工作区模式表示用户选择将工作区内全部可监控资源纳入目标范围，不表示宿主、文件系统和权限在任何环境下都能提供完整事件流。DiffTracker 分别呈现有效监控范围和监听覆盖；当权限、系统 watcher 配额、宿主排除或其他平台限制导致覆盖缺口时，模式仍可启用，但必须显示“覆盖受限”、受影响路径及原因，并提供重新检查入口。覆盖缺口中的资源保持未核验语义，不能因缺少事件而显示为没有变化。

正常支持的全工作区场景必须通过真实 Extension Host 验证，不能用“覆盖受限”掩盖缺失的基本实现。DiffTracker 不为追求表面完整性自动修改 VS Code 设置、不静默排除目标路径、不自动退回规则模式，也不增加周期性全盘轮询；必要的补充监听必须有界、可释放，并在失败时保留可见的不确定状态。

设置侧边栏分别显示用户请求的范围模式和实际状态，不以单一 On/Off 图标同时代表两者。实际状态至少区分：规则模式已生效、全工作区模式已生效、等待确认、准备基线、覆盖受限、配置无效、切换失败、旧规则兼容模式和录制已停止。覆盖受限时显示受影响数量及原因，并允许用户按需查看具体路径；常态进度和诊断不逐条输出路径。

对于 `files.watcherExclude` 等宿主层可能抑制事件的已纳入目录，DiffTracker 必须尝试安装有界、可释放的补充监听，而不能只从 ignore matcher 中移除规则。补充监听失败时，以最小已知目录或子树记录覆盖缺口，说明原因和“后代覆盖未确认”，而不是为每个后代生成虚假的待审变化。扩展不自动修改宿主设置。

重启可以恢复已确认的有效范围和审阅基线，但不能复用上次运行的覆盖正常结论。每次启动都重新安装监听并核对恢复期间状态，成功后才显示覆盖正常；权限、配额、配置版本或监听安装问题继续显示覆盖受限或恢复受阻，不要求用户重复同一范围确认。

覆盖恢复时先建立监听，再对受影响子树与已保存基线进行有界核对。核对证明的变化进入待审，无法证明的路径继续保持未知；仅仅成功创建 watcher 不能清除覆盖缺口，也不能把检查时状态自动接受为新基线。重新检查由用户操作或重载、设置变化等明确事件触发，不增加周期性扫描。

全工作区模式生效后新增、移除或重命名工作区根属于范围边界变化。DiffTracker 暂停录制并保留既有审阅，重新校验根级规则，并在列出当前全部根后要求用户重新确认；新根只有在范围准备和持久化成功后才加入有效范围，不猜测迁移旧根身份。

Changes badge 只统计待审资源：文本、不透明、未知以及范围外保留审阅都计入总数，覆盖缺口不作为文件变化数。Changes Tree 可进一步拆分文本、不透明、需处理和范围外保留审阅数量，并单独列出覆盖缺口子树；覆盖缺口不证明其中每个文件都已修改。

Settings 负责完整范围模式、请求／有效状态、规则编辑、迁移和重试；Changes Tree 只显示会影响审阅的简短范围警告和诊断入口；状态栏只显示最高优先级运行状态，其 tooltip 提供范围与覆盖摘要。状态栏优先级为恢复阻塞或范围失败、范围准备、覆盖受限、录制中、已停止，且不把覆盖缺口加入变化 badge。
