# Code Diff Tracker：产品边界与路线图

> Product boundaries and roadmap — local change visibility first; binary backup is optional, not a prerequisite.
>
> 更新日期：2026-09-20。本文是产品规划，不是已交付功能列表或发布日期承诺。
> **0.8.x 是当前核心目标，可以作为长期维护的完整产品。0.9.x 及以后仅保留为待重新决策的候选方向。**

## 1. 产品愿景

Code Diff Tracker 是一个轻量的本地变更审阅工具：在一次工作期间，帮助用户看见工作区内文件发生的变化。支持的文本文件可以详细审阅并按现有安全规则处理；其他文件至少能够被看见和确认。

主要使用场景：让 Agent、CLI、脚本或其他程序处理本地文件后，检查它们影响了哪些路径。其中一些文件不适合上传，也不需要纳入 Git 版本管理，但仍然值得监控。

这里的“本地”指文件所在的扩展宿主环境；远程工作区不等于数据一定保存在桌面电脑上。规划中的监控能力不要求上传文件、不要求 Git 跟踪文件，也不要求创建私有 Git 仓库。Git 自身可以只在本地使用；本产品解决的是“不必纳入版本管理也能观察变化”，而不是把 Git 等同于云端上传。

**产品不是通用备份系统、Git 替代品、逐次写入审计系统，也不是能够仅凭文件事件判定修改进程的取证工具。**

## 2. 版本安排与承诺等级

| 版本或方向 | 定位 | 范围与状态 |
| --- | --- | --- |
| 0.7.2 | 当前生产基线 | 保留已验证的文本审阅、安全恢复、Session V3 与 opaque identity 基础；0.8.x 在此之上补齐用户可见文件级审阅和监控范围。 |
| 0.7.x | 按需修复 | 出现新的明确缺陷时维护；不是进入 0.8.0 前必须再做一轮的开发阶段。 |
| 0.8.0 | 下一阶段核心目标 | 在明确的监控范围内补齐文件级记录；保留文本审阅，增加非文本状态展示、确认和本地监控范围控制。 |
| 0.8.x | 完善并长期维护 | 加强恢复一致性、监听覆盖、资源控制、异常提示和易用性。达到验收条件后，可以不再扩展产品范围。 |
| 0.9.x 候选 | 可选的整文件恢复 | 仅在重新确认真实需求、资源预算和安全方案后立项，不属于 0.8.x 的交付依赖。 |
| 更后续候选 | 特定类型的比较视图 | 图片等专用比较可单独评估；不承诺支持任意格式，不要求先建设通用备份系统。 |
| 1.0（若采用） | 稳定性与契约成熟度 | 不以二进制 Revert、图片 Diff 或完成所有候选功能为前提；最终编号另行决定。 |

“0.9.x”是保留讨论的路线标签，不是排期。未启动的候选项可以推迟、取消或转为独立扩展。本文不修改扩展版本号，也不意味着已有功能获得更强的安全保证。

## 3. 现有基础：保留什么，不顺手重写什么

核对日期当天，仓库 [package.json](../package.json) 的版本为 `0.7.2`。S0 的实现差距与测量见 [foundation findings](./s0-foundation-findings.md)。当前行为和限制见 [中文说明](../README_CN.md)、[英文说明](../README.md)；本文不是对 Marketplace 当前安装包的独立核验。

当前文本基线以完整字符串保存，并随工作区 session 持久化。扩展通过 `context.storageUri` 初始化 tracker；状态、备份和归档保存在这个工作区级扩展存储位置，而不是借用项目的 Git 历史。[实现入口](../src/extension.ts) / [状态与持久化实现](../src/diffTracker.ts)。

当前实现有单个受支持文本文件 5 MiB、快照条目数 10,000、单份序列化 session 状态 50 MiB、Revert 历史最多 10 条等限制。50 MiB 不是包含备份、归档和临时文件后的整个目录总占用承诺；当前也没有按天清理的通用保留策略。未来调整这些限制，需要独立验证，而不是在功能扩展时直接放大。

当前已经有 opaque baseline identity 基础：稳定的不支持文本资源可以保存存在性、size、mtime 和 SHA-256 fingerprint，并保留 dirty editor、扫描不确定性和 rollback 安全边界；但统一的用户可见文件级记录、Acknowledge、混合批量动作和范围模型仍属于 0.8.x 工作。当前仍不保存非文本内容副本，也不能把读取失败当成文件不存在。

0.8.x 不重写已经验证的文本 Diff、块级 Keep/Revert 和安全恢复算法。应在其外围分离“文件记录”与“可执行能力”，并继续遵守过期审阅拒绝、未保存缓冲区保护、Git 上下文隔离和持久化失败保护。

## 4. 0.8.x 的明确边界

### 4.1 记录层与文本审阅层分开

“不适合文本比较”不等于“不值得记录”。PNG、PDF、XLSX、模型文件、超大文本和不支持的编码，都可以拥有文件级记录；但读取失败、基线未知与正常的非文本类型不是同一种状态。

| 能力 | 受支持文本文件 | 可读取但不做文本比较的文件 | 不可读或基线未知的路径 |
| --- | --- | --- | --- |
| 文件级可见性 | 显示变化 | 显示变化或已观察事件 | 显示不确定性和原因，不静默忽略 |
| 新增、修改、删除 | 按已知基线判断 | 有足够存在性或内容证据时判断 | 只报告有依据的部分，不猜测原状态 |
| 具体内容比较 | 保留文本 Diff | 不提供文本 Diff | 不提供伪造 Diff |
| 确认操作 | 保留现有 Keep | 版本核验后确认当前状态 | 不能用普通 Keep 把未知状态伪装成已核验基线 |
| 块级操作 | 保留现有安全规则 | 不提供 | 不提供 |
| 整文件 Revert | 保留现有安全规则和限制 | 不提供 | 不提供 |
| 新增基线存储 | 完整文本及现有恢复信息 | 状态、元数据和有预算的内容指纹 | 已知信息及不可用原因 |

能力判断不能只看文件扩展名，也不能简单定义为“所有 opaque 文件都允许确认”。内容类别、基线是否已知、当前读取是否稳定、审阅版本是否有效和允许执行的动作，应分别表达。

界面应显示文件类型、相对路径、已知状态、可用的大小信息和能力说明。不显示虚假的 `+0/-0`，不把正常非文本文件当成故障，也不在 Tree、Review All、WebView 或批量统计中漏掉它们。

批量文本 Revert 不得触碰非文本内容，应明确报告跳过的文件和原因。混合文件的批量确认需要说明作用范围；失败或不确定的条目必须保留，不得显示为“全部已完成”。

### 4.2 非文本只保存比较参照，不复制文件本体

0.8.x 不为新增的非文本监控能力保存 PNG、PDF、模型等原始内容副本，不引入 blob 仓库、base64 内容快照、私有 Git 或多版本内容历史。

概念上的记录包括：路径与工作区身份、基线存在性、当前存在性、类型、已知大小、可获得的完整指纹、最近观察时间、核验状态和不可用原因。字段名称和持久化 schema 在实现阶段确定，不在路线图中提前锁定接口。

必须区分“已知存在”“已知不存在”“未知”。空文件、无法读取的文件和不存在的文件不能共用空字符串语义；时间戳应区分文件元数据时间与插件观察时间。

文本文件仍按现有机制保存完整基线。因此，“非文本不复制”不等于“整个扩展不保存文件内容”，本地存储也不等于加密存储。将私密文本纳入监控时，必须说明其文本基线可能留存在扩展存储中；记录、诊断和导出也不应未经明确操作暴露内容。

文本变成非文本、文件变大或变得不可读时，不得顺手删除已有的文本基线及恢复保护；这些既有记录仍按原会话规则管理。此例不代表新功能开始备份非文本本体。

### 4.3 “确认变更”不是“已经备份”

建议非文本使用“确认变更 / Acknowledge”，而不是暗示同时提供恢复能力的 Keep/Revert 组合。

对获得完整且稳定指纹的文件，确认必须绑定用户看到的版本。确认前再次核验，当前版本未变且持久化成功后，才能推进比较参照；随后再次变化，应重新进入待确认状态。确认操作不得修改工作区文件。

如果只有文件事件或大小、mtime 等元数据，可使用单独的“已阅此提示”语义，但不能声称内容已经核验，也不能用弱证据覆盖已有的强指纹。不可读、覆盖缺失或基线未知的警告仍应可见，直到重新核验、显式调整范围或建立新基线。

“确认后可以恢复”不是 0.8.x 的承诺。没有保存旧内容，就不能提供非文本 Revert。

### 4.4 监控范围不由 Git 单独决定

默认保持合理排除，避免依赖目录、缓存、构建产物和临时文件淹没列表；同时允许用户明确加入不进入 Git 的文件或目录。例如，`private-data/` 继续留在 `.gitignore` 中，但加入插件的本地监控。

建议采用以下优先级，并在路径检查工具中解释最终决定：

1. 安全边界与硬排除：工作区外目标、危险链接解析、Git 内部数据、插件自身状态与恢复临时文件等，不被普通包含规则放行。
2. 用户明确的插件排除规则。
3. 用户明确的插件包含规则，可覆盖普通默认排除与 Git 忽略策略。
4. 其余路径使用默认监控与忽略策略。

“配置上允许”不等于“实际已监听”。被宿主或文件监听设置排除的路径，必须建立经验证的监听或有限补查；做不到时应显示覆盖不足，而不是声称正在完整监控。不得为一个包含规则全局关闭宿主的所有忽略设置。

新加入范围的已有文件，不应自动标为本次新增。需要显式从当前状态建立比较参照，并说明此前的变化无法追溯。嵌套目录、多根工作区、规则变化和目录导入都必须遵守相同语义。

### 4.5 检测强度、活动提示和来源归因有边界

保存指纹的空间远小于复制文件，但计算完整指纹仍要读取内容。实现必须限制并发、重复读取、扫描范围与计算预算，不能因为“只存 metadata”就默认扫描开销可以忽略。

对能够在预算内处理的文件，使用完整内容指纹并检查读取稳定性；持续写入或读取期间被替换时应重试或降级为未核验。超大文件、受限文件及预算耗尽的情况，明确显示“检测到事件，内容未完整核验”或“监控覆盖不足”。采样指纹及相同 size/mtime 不等于完整内容一致证明。

应区分两个问题：

- **当前是否不同于基线？** 由存在性和内容证据回答。
- **这段时间是否观察到活动？** 由实际收到的事件回答，不宣称覆盖每一次写入。

在 0.8.x 体验完善中，可保留有界的活动标记及首次/最近观察时间；即使内容恢复为基线，也能提示期间观察到活动。此类提示应与当前差异分开计数，并允许确认，不建设无限事件流水或内容历史。

文件事件可能没有修改者身份，也不必然意味着内容变化。产品用语应是“工作期间观察到变化/事件”，而不是未经证实的“由某个 Agent 修改”。不为精确归因增加系统级进程审计或强制 Hook。

关闭扩展或停止监听期间，只能在重开后对可获得的当前状态进行核对；无法恢复中间发生后又被撤回的写入。删除后新增也不能仅凭时间接近就断言为重命名。

### 4.6 存储、清理与升级保持轻量

沿用工作区级扩展存储，保存有界的当前比较参照、待确认记录和必要的安全恢复信息。非文本 metadata 仍需要条目数与序列化大小限制；现有备份、归档及临时文件也计入资源评估。

不按文件总大小复制非文本，不因每次变动生成永久历史文件，不在 0.8.x 引入通用 blob GC。也不能因为达到配额或年龄阈值而静默淘汰仍被待审记录或恢复操作使用的基线。资源不足时，保留原安全状态并明确报告限制。

新基线、显式清除、范围变动和正常状态覆盖时，按既定生命周期清理已不需要的记录。停止监听、清除审阅数据和删除工作区文件是不同操作，必须保持明确区分。需要增加清理入口时，应说明是否包含备份与归档，而不是笼统承诺“全部删除”。

升级持久化 schema 时，旧文本基线和待审项必须保留。旧版本只留下未解析原因的非文本文件，不能在升级时通过读取当前文件倒推出过去的 hash；应保留未知状态，等待用户明确建立新的比较参照。

## 5. 0.8.x 验收与开发约束

0.8.0 首发重点是可见性、范围控制、确认语义和状态安全；活动提示等体验增强可以留在 0.8.x。是否完成以验收结果为准，不以新增格式数量为准。

| 验收场景 | 必须满足的结果 |
| --- | --- |
| 无 Git 工作区、未跟踪文件、显式包含的 Git 忽略文件 | 在实际覆盖范围内可监控，不修改 Git index、不要求上传。 |
| 已有和新增非文本文件的修改、删除、重建 | 有依据地显示状态；未知不能被伪装成新增或未变化。 |
| 空文件、同大小内容改写、重复通知 | 空文件与缺失可区分；通知触发的核验不只比较大小；列表不重复膨胀。 |
| 超大文件、读取失败、持续写入和读取中替换 | 有界开销，保留未知/未核验状态，不错误推进基线。 |
| 文件夹导入、嵌套忽略、规则变动和多根工作区 | 范围判定与真实监听一致；新纳入路径不伪造历史。 |
| 文本与非文本相互转换、超过大小或编码限制 | 不丢弃已有基线和保护信息，不把原始 bytes 经错误解码写回。 |
| 确认过程中再次变化、旧视图操作、持久化失败 | 拒绝过期操作或保留待确认项，不出现假成功。 |
| 重启、旧 session 迁移、缺失存储和数据损坏 | 保护已有文本状态；无法重建的非文本过去状态保持未知。 |
| 分支、worktree、工作区和录制生命周期改变 | 延续现有隔离规则，旧动作不能作用于新会话。 |
| 混合文件的 Tree、Review All、WebView 和批量动作 | 不漏项、不伪造行统计、不执行非文本 Revert，明确部分完成。 |
| 监控关闭、扫描预算或监听覆盖不足 | 不暗示完整历史或完整覆盖，提供可理解的状态。 |
| 现有文本审阅及恢复回归 | 原有安全回归通过；不得为扩展文件类型绕过既有保护。 |

实现只增加当前需求所需的记录分类、能力判断、监听和持久化支持。不预先建设备份引擎，不为候选功能重写成熟的文本路径，也不以增加 `kind` 字段为由展开整个仓库重构。

建议按“记录模型与迁移 → 检测和范围 → 确认及 UI → 回归和资源验证”拆分审查。实现前再细化技术任务与预算；本文本身不构成启动实现或发布的指令。

## 6. 0.9.x 及以后的候选路线（未立项）

保留这些方向是为了避免丢失思路，不是要求逐级完成。它们不能成为推迟 0.8.x 的理由，也不能让不使用这些能力的用户承担默认扫描、备份或存储开销。

### 6.1 候选 A：选择性的非文本整文件恢复

可能的需求是：用户明确选中的少量文件，需要在误改或误删后恢复上一份基线。不是“任意文件都能恢复”，也不是自动复制整个工作区。

若重新立项，前提包括：

- 显式启用和文件/目录范围选择，单文件、工作区和历史容量均有预算；超限路径仍能继续 0.8.x 级别的监控。
- 在修改前获得可靠的旧字节内容或可信旧版本来源。事后计算 hash 无法还原过去；基线未成功保存前，不能显示可恢复。
- 内容单独存储，不塞进文本 JSON。可以评估内容寻址 blob、去重和限量基线，但不预先决定必须采用 Git。
- 恢复覆盖、删除、新文件和目标竞争都需要独立安全设计；仅在写入前检查一次 hash 不构成整个操作期间的并发保证。不能保证时应拒绝自动恢复。
- 保留被当前基线、待审项、恢复记录、事务和可恢复备份/归档引用的内容；清理只能删除已证明不再需要的对象。不能只扫描主 JSON，不能按年龄删除仍被引用的内容。
- 磁盘满、异常退出、损坏、恢复中断及停用后的数据处置可测试、可解释；普通用户可查看占用并执行有明确范围的清理。

默认只评估受限的整文件基线与恢复，不承诺长期多版本历史、二进制块级编辑、任意 ACL/权限还原或任意文件系统的安全写回。

### 6.2 候选 B：图片等特定文件类型的比较视图

可能提供已有旧版本与当前版本的并排或专用比较。需要先明确两份输入的可靠来源；只有 metadata 或 hash 时，无法凭空生成旧图。

该方向可独立于通用非文本备份评估，也可依赖用户明确提供的版本或已存在的可靠来源。没有旧内容时只能打开当前文件预览，不能称为历史 Diff。

只选择真实有需求、维护成本可接受的类型；不承诺所有 custom editor 都支持历史比较，不为“格式齐全”自行解析所有 PDF、Office 或模型文件。接入外部查看器的权限、内容暴露和生命周期需要另行审查。

### 6.3 重新立项的门槛

候选功能只有在以下问题均有答案后，才进入实际版本计划：

1. 有具体使用场景，说明 0.8.x 的看见与确认为什么不足；独立备份工具或现有工作流为何不能更简单地满足需求。
2. 有代表性文件集、性能/容量预算、停用与清理策略，以及不影响轻量模式的证据。

## 7. 路线图维护原则

新需求先判断属于“0.8.x 核心完善”“可选候选”还是“超出产品范围”。变更本文件时应说明问题、必要性、资源影响和是否改变用户承诺。

README 与发布说明只描述已实现且已验证的能力；路线图明确区分目标与候选。发布前修复属于实际发布版本，不为解释开发过程虚构历史版本。

**最终原则：文本可以审阅和安全处理，其他文件可以看见与确认；通用备份和版本管理不是这个插件必须承担的责任。**
