## 1. 支持范围与交付判断

### 1.1 主要场景可靠，能力不足时明确退出

核心范围是已有验证的 Windows/Linux 本地工作区。真实 Host 组合沿用 Stable Windows、Stable Ubuntu、VS Code 1.80.2 Ubuntu，不扩写成所有平台与版本均已验证。

- 在有效范围和现有容量内，正确呈现文件创建、修改、删除及不确定状态；不要求文件进入 Git。
- 保留文本 Diff、文件/完整块 Keep/Revert、Undo/recovery 和过期操作保护。非文本可在可靠身份核验后 Acknowledge，不承诺内容恢复。
- 保留结构化范围规则、字面路径包含、非否定的 gitignore 风格显式排除，以及原有大小写、Unicode、别名和硬链接安全语义。
- Rules 遵循普通忽略，显式包含可覆盖普通忽略；Whole Workspace 不以普通忽略决定成员。两者均遵守显式排除和不可监控边界。
- 重启与恢复保留基线和已有待审证据。证据不足时显示未知、覆盖缺口或暂停，不伪造 Ready。

产品维护当前可观察状态相对于审阅基线的差异，不承诺每次瞬时写入的完整历史。特殊文件系统、无法验证的路径身份、复杂规则和超限目录不要求自动兼容成功；必须由实际保护和代表性验证支撑拒绝，不能仅在文档中标为「不支持」。已有有效规则不能被静默忽略、改写或绕过。

### 1.2 异常安全退出

| 情况 | 必须保留的结果 |
| --- | --- |
| 范围准备失败、取消、超限 | 不发布半成品范围；保留旧有效范围和已有待审证据。首次准备未完成时不伪造 Ready。 |
| 扫描或身份预算耗尽 | 停止昂贵工作；已有可靠证据可继续使用，无法判定的部分显示未知、缺口或暂停，不能视为排除或无变化。 |
| watcher 额度、安装或运行时覆盖失败 | 显示实际影响范围；不能安全局部降级时暂停。安装或扫描成功本身不能清除未完成的覆盖核对。 |
| 必要缺口、状态或失败证据无法保存 | 保留最后有效状态和待审证据；不能只弹错误后继续显示正常录制。 |
| 回滚、动作前验证、身份或视图映射不可靠 | 拒绝不安全操作，不猜测目标、不合并不同硬链接名称、不扩大用户选区。 |

安全底线是：不误改文件、不丢已有待审记录、不把漏监控显示成没有变化、不因失控工作量持续阻塞编辑器。安全拒绝不要求关闭整个产品；能可靠局部表达时保留已有能力。

支持场景的主要流程失效，或已知可达问题违反这些底线且尚未修复或可靠阻断，属于阻塞。必需 CI 尚未通过也不能标为完成。已可靠拒绝的范围外场景、兼容性增强和历史讨论整理本身不阻塞；已知严重风险仍需有边界的核验，不能仅因缺少新测试就忽略。

## 2. 保留的架构与资源边界

**后端唯一权威。** baseline、session/epoch、review token、stale protection、Keep/Revert/Acknowledge、Undo/recovery、opaque/unknown、Git context、scope、coverage、持久化和 rollback 均由 DiffTracker 管理。原生 UI 不维护第二套审阅状态。

**Native Review 仅作稳定 API 薄适配。** 沿用 Diff、宿主可用的 Multi Diff、Quick Diff、菜单与命令入口；能力不足或目标映射不可靠时退回现有安全入口。不依赖 Copilot 私有 UI、proposed API 或 `enabledApiProposals`。任意块内部分行操作继续延期。详见 [ADR-0019](./adr/0019-native-review-as-stable-api-adapter.md)。

**范围与覆盖分离。** requested / consent / effective / runtime coverage 四层状态、Scope Revision、Policy Fingerprint、Coverage Generation、Session V4 迁移与旧版降级阻断继续保留，不能用旧 `scanCoverage` 单独证明当前运行时覆盖。

**W1 保留，接管标准不扩大。** temporary imported bridge 与 persistent supplemental watcher 分别拥有资源，共享现有总预算。接管成功后释放临时 bridge；仍提供覆盖的长期 watcher 不为「数量归零」而关闭。不能证明接管成功时维持缺口或暂停。创建 watcher、完成扫描或收到未关联事件均不足以单独证明成功。详见 [ADR-0020](./adr/0020-provable-watcher-handoff-coverage.md)。

不提高现有容量、身份扫描或监听上限，不把不同用途的限制合并为统一文件数。后续批次不借状态同步改变依赖、持久化格式、规则语言或版本号。

## 5. S4-C：已合并的有限实现与验收

**目标：**导入典型已填充目录后，在不丢失已有待审证据的前提下，从 temporary bridge 过渡到可信长期覆盖，再释放临时资源。依赖已合并 S4-B，沿用 [ADR-0020](./adr/0020-provable-watcher-handoff-coverage.md) 的 ownership / generation 与有界核对契约。

**典型闭环：**导入包含尚未进入 Git 文件的目录 → 建立重叠覆盖并核对 → 安全接管 → 回收临时 bridge → Keep 后的后续编辑仍可见。接管期间发生修改或 restart/reload，不能因过早释放 bridge 静默漏记。

实现、V4 重启义务、失败兜底、代表性回归和保留限制统一记录在 [S4-C checkpoint](./s4c-handoff-checkpoint.md)。PR #17 已合并，最终 head 与主线 CI 见第 4 节；S4-D 沿用这些能力完成验收，后续不重复实现。

## 7. 执行与审查纪律

每批先写清解决的问题、保留的用户语义和不做的范围。默认一个 checkpoint，单个 work turn 最多两个；先恢复 CI 基线，再处理下一批，不将修复、审查和新发现串成无限循环。

P1/P2 是核验线索，不自动扩展支持承诺。按「触发场景 → 是否影响当前承诺或底线 → 修复/可靠阻断证据 → 阻塞、延期或待补证」留下短记录。已修问题引用提交与保留测试；过时和重复意见交叉引用，不以关闭线程掩盖风险，也不要求历史线程归零。

新增回归应先证明能捕获旧缺陷。CI 失败保留首次证据，原样重跑必须有依据；不能通过删有效断言、放宽业务预期或无限重跑换绿色。代码提交、测试通过、审查完成、PR 合并、版本发布分别陈述，未返回的结果不写成完成。
