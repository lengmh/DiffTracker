## 1. 修订原因

原 0.8.x 计划的 S0–S6 阶段顺序保持有效，但后续 Native Review / watcher 调研补充了两组关键证据：

1. VS Code 稳定 API 可以提供 Diff、Multi Diff、Quick Diff 和普通文本 selection，但 Copilot 内部逐行 Keep/Revert UI 不是 Marketplace 扩展可依赖的公共能力。
2. 创建 VS Code watcher、完成一次扫描或收到未关联事件，都不能单独证明 imported-directory bridge 已被安全接管；`files.watcherExclude` 还可能形成宿主监听盲区。

因此不重排主阶段，而是扩大 S0 的验证职责，并重新明确 Native Review 与 W1 的最终落点。

## 2. 冻结的架构决策

### 2.1 DiffTracker 后端是唯一权威状态源

baseline、session/epoch、review token、stale protection、Keep/Revert/Acknowledge、Undo/recovery、opaque/unknown identity、Git context、rollback、monitoring scope 和 runtime coverage 继续由 DiffTracker 后端管理。

VS Code 原生 Diff / Multi Diff / Quick Diff 只作为展示和动作目标选择 adapter，不维护第二套 review state。

### 2.2 Native Review 只使用稳定 API

生产路线不依赖 proposed diff gutter/hunk API、Copilot 私有 UI 或 `enabledApiProposals`。最低支持宿主不具备 Multi Diff 时保留单文件 Diff 或现有审阅入口。

完整 block 可以映射到既有事务；任意 block 内部分行 Keep/Revert 只有在后端存在独立 range/line action contract 后才能启用，因此不属于 0.8.0 完成门。

### 2.3 PR #6 是 architecture spike

PR #6 `spike/native-review-poc` 用于证明能力边界，关闭而不合并。有效结论已进入 S0：

- 原生 Diff / Quick Diff 可复用现有 virtual baseline。
- Multi Diff 在较新宿主可用，最低支持版本需要 fallback。
- virtual `diff-tracker-original:` 与真实 `file:` 文档可能共享 `fsPath`。
- working-document lookup 必须同时校验 URI scheme。
- PoC adapter、临时菜单和宽松映射不直接进入生产。

正式 foundation 由 PR #7 落地。

### 2.4 W1 采用“早验证、晚实现”

W1 production implementation 仍完整属于 S4，但 S0 提前验证 capability/contract。

S0 已确认：

- 当前 256 hard cap 约束 imported-directory direct watcher bridge 的活动资源数量，不是单一目录的文件数量限制；S4 引入 supplemental watcher 后，两类资源必须分别计数并共享统一总预算；
- string glob / RelativePattern 不能证明独立 coverage ownership；
- 简单 VS Code watcher 不能可靠恢复测试中的 `files.watcherExclude` 子树；
- DiffTracker 明确拥有的 direct watcher 可以作为 supplemental coverage 基础；
- “watcher 已创建”“扫描完成”“收到一次事件”均不足以证明 handoff 完成。

S4 必须区分 temporary imported bridge 与 persistent supplemental watcher。handoff 后“归零”的目标是 temporary bridge；仍承担真实覆盖的 supplemental watcher 不应为了指标而关闭。
